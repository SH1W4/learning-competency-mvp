# Visual System Specification — v0.1

**Status:** working specification / hypothesis  
**Owner:** JP Fernandes — UX/UI, Interface & Product Presentation  
**Scope:** identidade visual, símbolo, aplicações e handoff inicial  
**Related:** BRANDBOOK_DRAFT.md · DESIGN_BRIEF_JP_FERNANDES.md · NAMING_EXPLORATION.md

> Este documento transforma a direção do brandbook em critérios de execução. Não fecha a marca, o nome ou o sistema visual definitivo.

## 01. North Star

A identidade deve comunicar:

**Aprendizagem × Competência × Evidência × Verificação**

e tornar visualmente compreensível a gramática:

**EXPERIÊNCIA → EVIDÊNCIA → INTERPRETAÇÃO → REVISÃO → ESTADO → PROVA**

O visual deve parecer uma infraestrutura de desenvolvimento e verificação — não uma plataforma de cursos, uma empresa de blockchain ou uma demonstração de IA.

## 02. Hierarquia de identidade

### Nível 1 — Símbolo
Elemento gráfico independente do nome. Deve funcionar em avatar, favicon, GitHub, WhatsApp e pequenas aplicações.

### Nível 2 — Identidade visual
Símbolo + tipografia + composição + elementos gráficos + regras de aplicação.

### Nível 3 — Marca verbal
Nome, assinatura e tagline. O nome ainda está em exploração.

### Nível 4 — Produto
A identidade deve entrar no produto sem substituir a clareza funcional da interface.

### Nível 5 — Infraestrutura
Attestation, verificação e Solana devem aparecer como infraestrutura quando necessário, não como centro da identidade.

## 03. Símbolo institucional v0

### Arquivos atuais

- `learning-competency-symbol-v0.svg` — base vetorial.
- `learning-competency-symbol-reference-flat.png` — referência visual plana.
- `learning-competency-symbol-reference-3d.png` — referência visual volumétrica.

### Leitura conceitual atual

- círculo externo: integridade, ciclo, verificação;
- quatro pontos/eixos: estrutura, conexão, referência;
- camadas centrais: desenvolvimento, estados e progressão;
- sustentação simétrica: suporte/estrutura;
- azul: sinal de destaque dentro de uma base neutra.

Estas leituras são hipóteses de design, não significados oficiais da marca.

### Regra

O símbolo não deve depender de:

- IA;
- blockchain;
- Solana;
- certificados;
- microcredenciais;
- moedas;
- nome definitivo.

## 04. Paleta

### Base visual

- Preto — base principal.
- Branco — contraste principal.
- Cinza — níveis intermediários.
- Azul — destaque controlado.

### Valores presentes no asset v0

| Função | Valor atual | Status |
|---|---|---|
| Preto | `#000000` | referência do asset |
| Branco | `#FFFFFF` | referência do asset |
| Cinza | `#D9D9D9` | referência do asset |
| Azul | `#1683FF` | cor de destaque exploratória |

**Importante:** esses valores vêm do símbolo v0 e não constituem ainda uma paleta de marca definitivamente aprovada.

### Regras

- Não adicionar gradientes como elemento padrão.
- Não transformar o azul em cor dominante.
- Não introduzir uma paleta extensa sem decisão explícita.
- Priorizar contraste e legibilidade.

## 05. Tipografia

O brandbook ainda não aprovou uma família tipográfica definitiva.

### Requisito atual

A tipografia deve ser:

- limpa;
- contemporânea;
- altamente legível;
- adequada a produto digital;
- compatível com linguagem editorial/técnica.

### Decisão pendente

Definir:

1. família principal;
2. pesos;
3. hierarquia de títulos;
4. corpo;
5. números/dados;
6. eventual fonte monoespaçada para elementos técnicos.

Não tratar uma fonte específica como definitiva antes dessa decisão.

## 06. Composição

Priorizar:

- espaço negativo;
- alinhamento;
- simetria quando fizer sentido;
- hierarquia clara;
- poucos elementos;
- estruturas geométricas;
- camadas;
- linhas finas;
- ritmo editorial.

Evitar:

- excesso de molduras;
- excesso de cards;
- decoração sem função;
- saturação visual;
- composição crypto-genérica.

## 07. Elementos gráficos derivados

Podem ser explorados a partir do símbolo:

- segmentos circulares;
- pontos/eixos;
- camadas;
- linhas de conexão;
- estados;
- trajetórias;
- estruturas modulares.

Qualquer elemento derivado deve preservar a linguagem do símbolo sem repetir o símbolo literalmente em todas as peças.

## 08. Iconografia

A iconografia futura deve privilegiar:

- formas simples;
- geometria consistente;
- alto contraste;
- poucos detalhes;
- leitura rápida;
- compatibilidade com interface digital.

Evitar ícones literais de:

- moedas;
- cadeias de blocos;
- robôs;
- cérebros;
- diplomas;
- capelos;
- foguetes.

## 09. Imagens e ilustrações

Quando imagens forem necessárias, priorizar:

- processos;
- pessoas em contexto de aprendizagem/trabalho;
- evidências;
- colaboração;
- análise;
- sistemas;
- estruturas;
- abstrações editoriais.

Evitar imagens genéricas de banco que façam o produto parecer uma plataforma corporativa de treinamento.

O símbolo pode ser usado como elemento gráfico, mas não deve ser sobreposto indiscriminadamente a toda imagem.

## 10. Interface / produto

A identidade visual deve apoiar a interface, não competir com ela.

O produto deve tornar visualmente distinguíveis:

**EVIDÊNCIA → INTERPRETAÇÃO → REVISÃO → ESTADO → ATTESTATION → VERIFICAÇÃO**

Regras importantes:

- evidência original não deve parecer igual à interpretação da IA;
- revisão humana deve ter sinal visual próprio;
- estado de competência deve ser claramente distinguível de certificado;
- attestation deve ser apresentada como prova do estado registrado;
- verificação deve ser apresentada como uma ação/resultado verificável.

## 11. Responsividade e escala

O símbolo e elementos principais devem ser testados em:

- 16–24 px: favicon/ícone mínimo;
- 32–64 px: interface/avatar;
- 128–256 px: avatar/GitHub/WhatsApp;
- 512 px ou mais: apresentações/capas;
- composição ampla: apresentações e documentação.

O teste de escala deve verificar:

- reconhecimento;
- fechamento das formas;
- espessura;
- contraste;
- ausência de detalhes que desapareçam.

## 12. Área de proteção e proporção

Antes da versão definitiva do símbolo, documentar:

- área mínima de proteção;
- proporção;
- tamanho mínimo recomendado;
- alinhamento com nome;
- relação símbolo × wordmark;
- versões horizontal, vertical e isolada, se necessárias.

Estas regras ainda estão **pendentes de definição visual**.

## 13. Fundos e versões

Preparar no mínimo:

### Principal
Símbolo sobre fundo escuro.

### Monocromática
Uma única cor, sem depender do azul.

### Invertida
Versão para fundo claro, se necessária.

### Reduzida
Versão otimizada para tamanhos pequenos, caso detalhes do símbolo exijam simplificação.

Não criar variantes arbitrárias apenas para aumentar o número de assets.

## 14. Usos prioritários

Primeira rodada:

1. GitHub;
2. WhatsApp;
3. apresentação do hackathon;
4. documentação;
5. tela inicial do MVP;
6. eventual site/landing page.

Depois:

- social;
- materiais de validação;
- templates;
- apresentações externas;
- materiais institucionais.

## 15. Do / Don't

### DO

- preservar alto contraste;
- manter simplicidade;
- usar o símbolo como sistema;
- preservar espaço negativo;
- diferenciar estados visualmente;
- manter consistência entre produto e apresentação;
- testar em tamanhos pequenos.

### DON'T

- alterar o símbolo para cada aplicação;
- adicionar neon por padrão;
- transformar o símbolo em ícone de blockchain;
- usar certificado como metáfora principal;
- colocar IA/robôs como linguagem visual;
- criar uma estética visual diferente para cada canal;
- fechar nome ou tagline sem validação.

## 17. Critérios de aceite

A frente visual não deve ser considerada concluída apenas porque existe um símbolo bonito.

Ela deve responder:

1. O símbolo funciona sem nome?
2. Funciona em tamanho pequeno?
3. Funciona em preto e branco?
4. Existe consistência entre símbolo, apresentação, documentação e produto?
5. A identidade comunica competência/evidência/verificação sem depender de blockchain?
6. A interface diferencia evidência, IA, revisão, estado e prova?
7. O sistema pode ser reproduzido por outra pessoa?
8. O material deixa claro o que é decisão e o que ainda é hipótese?

## 18. Decisões ainda abertas

- tagline definitiva;
- família tipográfica;
- valores finais da paleta;
- versão definitiva do símbolo;
- área de proteção;
- tamanhos mínimos;
- wordmark;
- sistema de ícones;
- padrões derivados;
- motion;
- templates finais.

## 19. Regra de governança

O design pode propor e testar.

A identidade não deve alterar:

- a tese do produto;
- o fluxo do MVP;
- a arquitetura;
- o modelo de competência;
- o papel da IA;
- o papel da revisão humana;
- o papel da attestation/Solana.

Se uma decisão visual exigir mudança de produto, isso deve voltar para a frente de produto/arquitetura.
