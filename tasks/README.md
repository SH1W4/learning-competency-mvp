# Task Map

> Operational backlog for evolving the Learning Competency MVP from foundation to a reproducible hackathon submission.

## How to use

Every task must have an Owner, Status, Dependency, Deliverable and objective Done when criterion.

Team members can assume tasks directly from this map. If ownership changes, update the task rather than relying on chat history.

## Priority order

M1 — CONCRETE USE CASE
↓
M2 — EVIDENCE + AI + REVIEW
↓
M3 — STATE + ATTESTATION + VERIFICATION
↓
M4 — VALIDATION + DEMO + SUBMISSION

Do not start downstream work that depends on an unresolved upstream product decision unless the task is explicitly marked as a parallel discovery task.

## Ownership rule

A task has one accountable owner. Other contributors may support it.

Use GitHub issues/PRs for implementation work. Use the task files for the execution map and acceptance criteria.

## Status legend

- TODO — ready to be assumed.
- IN PROGRESS — owner is actively executing.
- BLOCKED — dependency prevents progress.
- DONE — acceptance criteria are satisfied and evidence is available.

## Current task groups

| Group | Objective | Primary output |
| --- | --- | --- |
| M1 | Choose and operationalize the first use case | Competency + trail + evidence contract |
| M2 | Make evidence interpretable and reviewable | Evidence → AI → review pipeline |
| M3 | Produce and verify a bounded state | State + attestation + Solana verification |
| M4 | Prove value and package the submission | Validation + demo + pitch + freeze |

## Definition of completion

The project is ready for hackathon submission when:

1. the first vertical slice runs end-to-end;
2. evidence provenance and AI interpretation are distinguishable;
3. human review changes or accepts the proposed state;
4. attestation represents the defined state/event;
5. verification is reproducible;
6. demand-validation evidence is recorded without invented traction;
7. demo and pitch describe only what the product actually does;
8. GitHub history makes the execution traceable.
